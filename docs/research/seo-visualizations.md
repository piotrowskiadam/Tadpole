# SEO site-structure visualizations: evidence for Tadpole design

Accessed: **2026-11-01**. Scope: public, first-party documentation for Screaming Frog SEO Spider, Sitebulb, Ahrefs Site Audit and Semrush Site Audit. Eight full pages were retrieved with Firecrawl; no authenticated product session or performance benchmark was run. Findings support design artifacts, not an implementation commitment.

## The distinction the interface must preserve

Three different structures appear across these products: **URL hierarchy** (protocol/host/folder containment), **crawl discovery** (one discovered or shortest-path parent per URL), and **actual internal links** (potentially many incoming/outgoing relationships). They answer different questions. Calling any of them simply “site structure” risks implying relationships the data does not contain. Screaming Frog explicitly documents this distinction, and Sitebulb states its crawl map is not a complete link map. [Screaming Frog guide](https://www.screamingfrog.co.uk/seo-spider/tutorials/site-architecture-crawl-visualisations/), [Sitebulb visualizations](https://support.sitebulb.com/en/articles/9887437-site-visualisations)

## Screaming Frog SEO Spider

**Views and questions.** Crawl and directory models each have force-directed, 3D force-directed and tree formats. The crawl model displays a single shortest path from the starting URL, helping explain click depth and discovery. If equally short paths exist, the first crawled link wins. The directory model groups URL components and paths; its edges are containment, not hyperlinks, and intermediate nodes may not resolve. It makes shared directory/template issues easier to spot. Node colors can expose non-indexability or response-code/segment patterns; size can express depth, unique inlinks or Link Score. [Official visualization guide](https://www.screamingfrog.co.uk/seo-spider/tutorials/site-architecture-crawl-visualisations/)

**Drill-down.** Users can focus a node, navigate by URL and use browser history. A node's inlinks/outlinks, or links involving its children, can be shown on demand; linked nodes are highlighted while the others fade. This is stronger evidence for a focused link neighborhood than for drawing every edge permanently. Tree orientation is configurable. Interactive HTML and static SVG exports support communication outside the tool. [Official visualization guide](https://www.screamingfrog.co.uk/seo-spider/tutorials/site-architecture-crawl-visualisations/)

**Documented scale.** The 2D crawl graph and crawl tree show up to **10,000 URLs per view**, with focus exposing another bounded section. Gray nodes indicate truncated children. The 3D crawl graph is documented as supporting **100,000 URLs**, in an external browser, with different interaction behavior. These are vendor display limits, not measured load-time or responsiveness guarantees. The vendor explains that omitting most internal edges makes graphs more scalable and interpretable. No worker, caching, streaming or GPU implementation details were verified. [Official visualization guide](https://www.screamingfrog.co.uk/seo-spider/tutorials/site-architecture-crawl-visualisations/)

## Sitebulb

**Views and questions.** Sitebulb documents six combinations: Crawl Map/Tree/Radial and Directory Map/Tree/Radial. Crawl views follow the first discovered link; directory views group URL paths and may include non-resolving grouping nodes. Trees emphasize parent/child levels, radial layouts emphasize hierarchy and folder groupings, and force-directed maps reveal broad shapes. Directory views offer little information when every page lives at the root. [Site Visualisations](https://support.sitebulb.com/en/articles/9887437-site-visualisations)

Examples show recognizable pagination chains, flat architectures and duplicated structures. Those shapes are investigation prompts, not automatic diagnoses: hover reveals the URL, depth and inlinks needed to interpret a pattern. The FAQ explicitly says physical edge length has no semantic meaning. [Crawl-map examples](https://sitebulb.com/resources/guides/crawl-map-examples/), [Crawl Maps FAQs](https://support.sitebulb.com/en/articles/9887471-crawl-maps-faqs)

**Drill-down.** Hover opens metadata; the context menu opens URL Details, copies/opens the URL, or rebuilds the graph from that URL. A URL bar can also change the root. Left-click focuses the camera. Settings update graph appearance live, including a non-indexable highlight. URL Details connects the overview to crawl-path inspection and exports. [Site Visualisations](https://support.sitebulb.com/en/articles/9887437-site-visualisations)

**Scale and conflicting documentation.** The newer visualization article (October 14, 2024) says both indexable and non-indexable URLs are mapped, up to **10,000 URLs**. The FAQ (September 17, 2024) instead says only internal indexable HTML URLs with incoming links are included, then describes depth-based child caps: all at depths 0–1, up to 50 at depths 2–5, 10 at depths 6–10 and one beyond depth 10; it also mentions further reductions above 10k/20k nodes. These pages cannot establish one consistent current inclusion algorithm. Treat the FAQ as evidence that pruning has been used, and the newer article as the better description of non-indexable highlighting—not as proof that the older limits still apply. Confirm in-product before copying rules. Neither page supplies latency measurements. [Site Visualisations](https://support.sitebulb.com/en/articles/9887437-site-visualisations), [Crawl Maps FAQs](https://support.sitebulb.com/en/articles/9887471-crawl-maps-faqs)

## Ahrefs Site Audit

**Views and questions.** The vendor's Site Audit feature guide documents a subdomain/subfolder tree with subsection distributions for HTTP status, link depth, organic traffic, referring domains and indexability, plus table/chart switching. It helps locate broken or deep sections and compare their traffic/backlink importance. This is a hierarchical reporting view with aggregated metrics; the source does not establish a force-directed all-links map. The article was last updated March 12, 2021, so exact current controls are unverified. Do not conflate it with Ahrefs **Site Explorer's** similarly named Site Structure report. [Site Audit feature guide](https://ahrefs.com/blog/new-site-audit-features/)

**Drill-down.** The same guide documents saved segments applying across Site Audit reports, composable filter presets, URL Info with incoming/outgoing link details, and previous-crawl comparisons in Data Explorer. A September 3, 2026 help article confirms that clicking an inlink count opens the pages linking to a broken target. This provides current support for an aggregate → URL → source-links workflow, although it does not reverify every 2021 tree control. [Feature guide](https://ahrefs.com/blog/new-site-audit-features/), [Current broken-link workflow](https://help.ahrefs.com/en/articles/1445888-how-do-i-find-broken-internal-links-on-my-site-in-site-audit)

**Scale.** No visualization-specific rendering cap, progressive-loading contract or latency target was found in these sources. Crawl quotas must not be presented as graph rendering limits. Aggregation and segmentation are useful design precedents, without implying a documented performance architecture.

## Semrush Site Audit

**Views and questions.** Site Structure is an expandable subdomain/subfolder report showing URL and issue counts per section. The Internal Linking thematic report combines crawl-depth distribution, incoming/outgoing link-count ranges, Internal Link Distribution, issues and a list of pages passing the most Internal LinkRank. These answer “which sections need work?”, “which pages are deep or underlinked?” and “where is internal authority concentrated?”. They are trees, distributions and tables; the retrieved documentation does not establish a full node-link network. [Crawled Pages / Site Structure](https://www.semrush.com/kb/543-site-audit-crawled-pages), [Thematic Reports](https://www.semrush.com/kb/959-site-audit-thematic-reports)

**Drill-down.** Expand directories to locate problematic subsections. Crawled Pages supports URL search, combined filters including depth/status/issues, configurable columns and sorting. Clicking a URL opens its attributes and expandable issues. Most crawlability charts navigate to filtered page reports; internal-link issues open detailed issue reports. This links summary discovery directly to actionable evidence. [Crawled Pages](https://www.semrush.com/kb/543-site-audit-crawled-pages), [Thematic Reports](https://www.semrush.com/kb/959-site-audit-thematic-reports)

**Scale and completeness.** Semrush explicitly warns that Site Structure is derived from crawled pages: crawl limits or scope restrictions can make it differ from the actual site. No visualization latency promise, virtualized-tree implementation or rendering threshold was verified. Its “Performance” report measures the audited website, not the speed of Semrush's visualization interface. [Crawled Pages](https://www.semrush.com/kb/543-site-audit-crawled-pages), [Thematic Reports](https://www.semrush.com/kb/959-site-audit-thematic-reports)

## Transferable decisions for Tadpole artifacts

The following are **design recommendations inferred from the evidence**, not claims that vendors implement the proposed mechanisms:

1. **Prioritize URL hierarchy and crawl tree as separate modes.** Show their edge meanings in the legend; label synthetic folders and the crawl starting URL. Add radial presentation only if it answers the same hierarchy question more clearly.
2. **Make actual links a focused neighborhood.** Selecting a URL/section can reveal incoming/outgoing links, counts and source/target rows. Default to a bounded useful view; expose the total, shown and hidden counts instead of silently dropping relationships. Screaming Frog's focused overlays and truncation indicators are the strongest precedent.
3. **Offer aggregate views before expensive networks.** A section-to-section link matrix and depth-versus-internal-rank scatter could answer cross-section flow and buried-important-page questions. These two specific views were **not verified as vendor features** here. Their justification is Tadpole's tasks and bounded visual complexity, informed by Ahrefs/Semrush metric aggregation.
4. **Draw loading and coverage states into the artifacts.** Specify a quickly visible summary, explicit user-triggered expansion, cancellable/retryable detail loading and preserved context when switching views. Differentiate “not crawled”, “filtered”, “hidden by display budget” and “zero links”. These are proposed requirements; no source proves a suitable Tadpole budget or latency number.
5. **Require measurement before selecting limits.** Benchmark payload, parsing, layout, rendering, first useful view and interactions independently on representative crawl sizes/devices. Vendor node caps are comparison evidence, not transferable speed guarantees. Do not make 3D a priority based solely on its higher documented node ceiling.

Unverified across the investigation: authenticated current UI behavior, accessibility/keyboard support, exact browser/device performance, layout technology, background computation, cache invalidation and incremental data delivery. Public docs supplied sufficient evidence for semantic modes and drill-down patterns, but not a production performance design.
